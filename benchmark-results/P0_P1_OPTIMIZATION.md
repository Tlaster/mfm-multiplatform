# P0/P1 性能优化报告

测试日期：2026-08-31
对比基线：完成官方 MFM 0.26.0 行为对齐、尚未应用本轮 P0/P1 的实现
优化版：当前工作区

## 结论

- JVM 的 1 MiB CJK 吞吐从 `1.043` 提升到 `86.634 ops/s`（**83.03×**），分配从 `178,960,438 B/op` 降到 `446 B/op`。
- JVM 稀疏、密集、复杂 Unicode Emoji 分别提升 **3.02×、1.32×、1.55×**；稀疏和密集 Emoji 分配分别降低 **83.33%** 和 **46.06%**。
- JVM 连续无匹配 `]` 在 4–128 KiB 上稳定提升约 **2.39×**；长 `<plain>` 提升 **1.82×**。
- iOS Simulator 上 CJK 提升 **163.78×**，稀疏/密集 Emoji 提升 **3.37×/1.76×**，连续 `]` 提升 **7.80×–8.55×**，长 `<plain>` 提升 **1.99×**。
- 原有 JVM 核心场景的吞吐变化为 `-2.86%` 到 `+7.62%`；所有负向项的 99.9% 置信区间均与基线重叠。iOS 常规场景变化为 `-1.99%` 到 `+2.08%`。
- JVM/iOS 测试均为 96/96 通过；官方差分集共 7,225 条输入，仍为 0 mismatch。iOS 两版全部 17 个 benchmark 的结果 hash 一致。

## 落地内容

P0：

- Unicode Emoji 先走无分配的码点范围快路径；简单 Emoji 不再构造整段编码副本，也不初始化完整正则。
- 只有 ZWJ、肤色、旗帜、tag sequence 等组合序列才进入懒初始化的精确正则。
- 非 Emoji Unicode 文本连续批量推进；码点读取不再产生 nullable `Char` 装箱。
- 连续且无法闭合 function frame 的 `]` 一次扫描完毕。

P1：

- Quote 使用单个 `StringBuilder` 完成换行归一化，不再创建逐行 substring、临时列表和 `joinToString` 结果。
- `</plain>`、`</center>` 的固定标记搜索改用 Kotlin 标准库 `String.indexOf`。

公共 `MFMParser.parse` 入口和 AST 行为均未改变。曾验证过通用 ASCII 标点批量扫描，但它会拖慢常见短富文本，因此未保留；1 MiB 标点控制组在最终实现中保持中性。

## 方法与验证

JVM：Apple M1 Ultra、Corretto 21.0.6、JMH 1.37、单线程、单 fork、`-Xms512m -Xmx512m`、3 × 1 s 预热、5 × 1 s 测量，并启用 `-prof gc`。

iOS：同一台主机上的 iPhone 17 Pro / iOS 27.0 Simulator，Kotlin/Native 2.3.0 `iosSimulatorArm64` release；每个场景独立进程，自适应到至少 500 ms/sample，3 次预热、5 次测量。

验证结果：

- `jvmTest`：96/96 通过。
- `iosSimulatorArm64Test`：96/96 通过。
- `compileTestKotlinWasmJs`：通过。
- 官方差分：150 default + 14 nestLimit + 130 full probes + 16 simple probes + 5,000 fuzz + 1,915 Emoji，全部 0 mismatch。
- iOS 17 个场景的两版结果 hash 全部一致。

精确数据见 [p0-p1-optimization.json](p0-p1-optimization.json)。
